#### 2. 제품 맥락과 개인 역할

KSTV5는 보안 관제/로그·설비/취약점 정보를 관리하는 기존 제품 코드로 보인다. 이번 조사에서 직접 추적되는 개인 업무 축은 **V5용 보고서 서비스 구성 및 UI 연결**, **보고서 성능과 실행 안정성 보완**, **관제 화면·통계·대용량 로그 내보내기 개선**이다. 제품 전체, SIEM 수집 엔진, 취약점 점검 스크립트 전체를 이 68건으로 개인 개발했다고 말하지 않는다.

`report-mgr`는 Spring Boot 2.7.18, Java 8, MyBatis/MariaDB, JasperReports 6.21.5를 사용한다. `ui-svr`의 `kst-siem-backend`는 Java/eGovFrame 계열이다. 이 기술 구성은 각 POM과 현재 코드의 근거이며 숙련도를 정량화한 수치는 아니다.

#### 3. 보고서 기능 이식·서비스 경계 정리

##### 3.1 V5 보고서 처리 서비스 구성

- **개인 변경:** `report-mgr`의 `163e0cc`(2026-09-10)는 V5 보고서 서비스의 초기 변경이다. 151개 파일을 포함한 큰 커밋이며 DTO, MyBatis mapper, Jasper JRXML·폰트 등 초기 이식 자료가 섞여 있다. 새로 창작한 코드량으로 해석하지 않는다.
- **현행 기능:** `ReportController`가 `/api/v1/report/kro`, `/krs`, `/wro`, `/wrs` 네 POST 진입점을 제공한다. KRO는 관제 개요, KRS는 기간 요약, WRO/WRS는 취약점 관련 보고서 서비스로 연결된다. 서비스별로 보고서 이력을 만들고, Jasper template에 데이터 소스를 공급하며, 파일을 내보낸다.
- **출력 형식:** `ReportUtil.exportReport`에는 PDF, XLSX, DOCX 내보내기 경로가 있다. `ui-svr`의 `3841d98`에서는 미지원 HWP 생성 코드를 제거하고, 필요한 경우 `report-mgr`에서 지원해야 한다는 변경 메시지를 남겼다. 이력서에 HWP 지원 구현이라고 쓰면 틀린다.
- **UI 경계:** `ui-svr`의 `3841d98`은 기존 `ReportServiceImpl`과 취약점 분석 보고서 구현을 축소하고 `ReportMgrClient`, `ReportMgrRequest`를 추가해 별도 서비스 호출로 바꿨다. 보고서 생성 책임을 UI 서버 밖으로 옮긴 변경이다. 3,276줄 삭제는 레거시 이관·삭제의 결과로, 성능이나 생산성 수치가 아니다.
- **배포 연결:** `6866af3`, `e6b355a`, `2913042`, `889370c`, `cae4475`의 커밋 체인은 실행 시간 관찰, UI 연결, 암호화/환경설정, 다운로드 경로와 이미지 상대경로 등 이식 후 연동 문제를 다룬다. 세부 기능의 최종 동작은 코드·운영 환경을 추가 검증해야 한다.

**근거 경로:** `report-mgr/src/main/java/com/fornet/reportMgr/report/controller/ReportController.java`, `report/service/{KstReportOverviewService,KstReportSummaryService,WeakReportOverviewService,WeakReportSpecificService}.java`, `common/util/ReportUtil.java`; `ui-svr/kst-security-server/kst-siem-backend/src/main/java/com/fornet/siem/common/client/ReportMgrClient.java` 및 `mvc/service/ReportServiceImpl.java`; 개인 커밋 `163e0cc`, `3841d98`.

##### 3.2 생성·이력 화면 통합

`ui-svr`의 `5a39ee2`(2026-09-21)는 기존 보고서·취약점 보고서의 화면/컨트롤러/서비스를 정리하고 `report.js`, `reporthistory.js`, `report.html`, `reporthistory.html`을 중심으로 생성 및 이력 화면을 통합했다. 변경에는 이전 화면과 스크립트 삭제가 많다. 포트폴리오에서는 **여러 보고서 진입점과 이력 확인 흐름을 재구성**한 업무로 설명할 수 있다. 사용자 클릭 수나 업무 시간 감소는 측정 자료가 없어 주장하지 않는다.

##### 3.3 자동 생성과 보존기간

현행 `ReportScheduler`에는 일간 관제 개요, 월간 관제 개요, 월간 요약, 새 취약점/전체 취약점 보고서, 보고서 보존기간 처리의 `@Scheduled` 메서드 6개가 있다. `scheduler.enabled` 설정으로 클래스 등록 여부를 제어하고 크론은 properties에서 읽는다. 자동 보고서의 기준 기간은 전일 또는 전월로 계산한다. KSTV6의 동적 스케줄러와 구분해야 한다. V5에서 DB 설정 변경 즉시 반영을 구현했다고 기술하지 않는다.

**근거 경로:** `report-mgr/src/main/java/com/fornet/reportMgr/common/scheduler/ReportScheduler.java`, `src/main/resources/application.properties`; 관련 커밋 `6866af3`, `8367a79`.

#### 4. 보고서 성능·안정성 보완 체인

##### 4.1 SQL 및 원천 데이터 조회

- `c36a92d`(2026-09-18)는 보고서 성능 문제를 다루며 `KROOrchService`, `KROService`, `KROMapper.xml`, `ReportUtil` 등을 수정했다. 오케스트레이션과 원천 조회 경계를 옮기고 조회 표현을 조정한 흐름이다.
- `22c70c6`(2026-09-28)는 KRO/KRS mapper와 `KRSSourceService`를 크게 수정했다. 예를 들어 KRO의 장비 IP 비교는 `inet_ntoa(b.ipaddr1)`로 컬럼을 변환하는 조인에서 입력 IP를 숫자로 변환해 저장 컬럼과 비교하는 형태로 바뀌었다. 같은 패치에는 쿼리 포맷 수정도 많으므로 모든 수정 줄을 성능 개선으로 계산하지 않는다.
- 현재 `ReportUtil.partitionTimeRange`, `partitionDateRange`, `calculateChunks`와 `KROSourceService`, `KRSSourceService`의 물리 L2 테이블 조회/집계 함수가 존재한다. 조회 범위 분할과 임시 집계 테이블 생성·정리의 구조적 근거다.
- `eaf80ac`에서 트랜잭션 경계를 조정했으나 `91bbcaf`에서 잠금 문제 때문에 일부 경계를 다시 제거했다. 이 두 커밋을 각각 독립된 성공 사례로 표현하지 않고 **운영 문제를 확인하고 트랜잭션 범위를 재조정한 체인**으로 다룬다.

**성과 표현 경계:** 쿼리 구조 및 대량 조회 경로 개선은 코드로 확인된다. 직접 작업한 `development/docs/README.md`에는 특정 검증 환경의 별칭별·API 실행시간이 기록돼 있다(§10.2). 측정 조건이 다른 결과를 섞거나 제품 전체에 “몇 배 빨라짐”으로 일반화하지 않는다.

##### 4.2 동일 보고서 중복 실행 제어

`8367a79`(2026-09-29)는 `ReportRunLock`을 도입했다. `ConcurrentHashMap.newKeySet()`으로 실행 중인 키를 관리하고, 보고서 종류·기간·장비, 요약 보고서는 선택 섹션까지 포함한 키를 만든다. 같은 키의 요청이 실행 중이면 중복 요청의 실패 이력을 기록하고 반환한다. 정상·예외 종료 모두 `finally`에서 키를 해제한다. 개요·요약·취약점 보고서 서비스에 적용된다.

**제한:** JVM 메모리 잠금이므로 코드 주석의 단일 인스턴스 전제에서만 유효하다. 분산 잠금 또는 다중 인스턴스 중복 방지를 구현했다고 쓰지 않는다.

##### 4.3 재시작 후 이력·집계 자원 정리

같은 `8367a79`에서 `ReportStartupCleaner`를 추가했다. `ApplicationReadyEvent` 후 미완료 보고서 이력을 실패 상태로 정리하고, UUID 형식의 `KRS_AGG_`, `KRO_WIN_`, `WRO02_` 임시 집계 테이블만 패턴 검사 후 제거한다. 조회·개별 삭제 예외는 로깅하고 다음 정리 작업을 계속한다. 목적은 프로세스 중단 시 남는 상태/자원의 정합성 회복이다. 실제 운영 장애 발생 건수 감소는 확인되지 않았다.

**근거 경로:** `report-mgr/src/main/java/com/fornet/reportMgr/common/{lock/ReportRunLock,lifecycle/ReportStartupCleaner}.java`, `meta/mapper/MetaMapper.java`, `src/main/resources/mybatis/mapper/maria/MetaMapper.xml`; 커밋 `8367a79`.

##### 4.4 취약점 보고서 판정 수정

`c2fbef6`(2026-09-29)는 `WROMapper.xml`, `WRSMapper.xml`과 영문 취약점 상세 JRXML의 취약 여부 표현을 수정했다. 이력서에서는 **취약점 보고서 판정/출력 정합성 보완**까지 기술할 수 있다. 실제 진단 정확도 향상률 또는 오탐 감소율은 시험 결과가 있어야 말할 수 있다.

#### 5. 관제 UI·통계·로그 내보내기

##### 5.1 장비 상태 전체 스캔

`ui-svr` `16796ec`(2026-09-22)는 장비마다 `mocalog_main`의 최근 수신 시각을 조회하던 N회 패턴을 배치 UPDATE로 변경했다. 변경 SQL은 최근 1일의 `create_time` 범위를 조건으로 두고 장비별 `MAX(create_time)`을 그룹화해 `moca_device`의 마지막 로그 시간을 갱신한다. 스케줄러의 호출부와 mapper 인터페이스도 함께 바뀌었다. **반복 조회를 집계 1회+배치 갱신 구조로 변경**한 것은 patch로 확인된다. 실제 실행시간 전후 값은 없다. “트랜잭션 개선”은 커밋 제목이며 코드에서 확인된 핵심은 조회/갱신 구조다.

##### 5.2 이벤트 분석 통계와 보존 범위

`c39536b`(2026-09-29)는 이벤트 분석 통계 보존기간 처리와 Windows 관제 쿼리/차트 변경을 포함한다. `ScheduledTasks`, `LogStatusMapper`, Windows Total/System/Security Top10 서비스·mapper, chart 공통 스크립트가 연동된다. `e5fe578`는 분석 탐지의 공격 IP·피해 IP·규칙 IP 통계 서비스/SQL을 수정했고, `0ebd86e`는 방화벽 추세 집계 SQL을 보완했다. 기능별 집계 조건과 표시 정합성을 다룬 작업으로 표현한다. 통계가 원래 얼마나 틀렸는지, 개선 후 오차가 얼마인지 수치는 없다.

##### 5.3 Windows 모니터링 목록 페이징

`a5eeefd`(2026-09-29)는 Windows Application/Security/System/Total Top10의 상세 목록에 `WindowLogCursorPager`를 도입했다. 물리 `l2_*` 테이블별 최신 시각을 기준으로 후보를 정렬하고, `(create_time, id)` 커서와 필요한 행 수로 여러 테이블의 결과를 합친다. 동일 시각의 행이 LIMIT 경계에서 잘리지 않도록 그 시각 전체를 다시 조회하는 처리가 있다. Java에서 동일 시각의 ID 순서를 확정하고 이미 충분한 최신 행을 얻었으면 더 오래된 테이블 조회를 건너뛴다. 연동 mapper와 chart 모달 호출도 수정했다. **대량 기간 검색에서 페이지별 조회 범위를 제어하는 구현**으로 기술한다. 성능 측정치는 별도 검증 전까지 기재하지 않는다.

##### 5.4 대량 로그 CSV·Excel 내보내기

##### 9.1 업무 흐름과 반영 경로

`업무방법.txt`에는 `tbl_weak_default`의 취약점 ID와 스크립트 컬럼을 확인하고, 보안 상세 가이드와 TODO를 참고해 수정한 뒤 에이전트에서 BAT 단독 실행 → 서버에서 DB 스크립트 변경 후 실행 → 두 단계 결과 확인 → 검토 요청·DB 원복 순으로 진행하는 절차가 적혀 있다. 이는 **정의된 시험 절차**의 근거다. 항목별 실제 합격 로그가 폴더에 함께 있는 것은 아니므로 19개 모두 양 단계 시험 완료라고 확대하지 않는다.

18개 Python 파일은 BAT 본문을 문자열로 담아 `tbl_weak_default.script`를 해당 ID에 UPDATE하고 commit하는 구조다. 각 파일의 포함 BAT 문자열과 동명 `.bat` 파일을 정규화해 대조한 결과 **18/18개가 일치**했다. `W-09`는 BAT만 있고 동명 Python은 없다. `W-09`와 `PC-04` BAT는 취약점 ID를 제외하면 동일한 서비스 목록 점검 로직이다. `runall.sh`는 18개 전체가 아니라 `W-21/24/26/27/64/74/78/79/82`의 Python 9개만 순차 실행하도록 구성돼 있다. 따라서 “19개 전부 일괄 DB 반영”이라고 말하면 부정확하다.

점검 BAT들은 `result.txt`에 항목 ID와 `ok`/`fail` 판정 형태를 출력한다. 단순 명령 실행뿐 아니라 **제품 에이전트가 소비하는 결과 형식**까지 맞추려 한 점이 확인된다. Python 파일에는 DB 접속 설정이 포함되므로 공개 자료에는 코드·접속값·내부 주소를 복사하지 않는다.

##### 10.3 패치 설계·설치 담당자 가이드·검증

`PATCH.md`, `patch.sh`, `patch/INSTALL_GUIDE.md`가 서로 대응한다. 폐쇄망에서 보고서 서비스 신규 설치와 UI 서버 교체를 위해 `patch.sh`는 **사전 상태 점검 → 백업·rollback 스크립트 생성 → 서비스 정지 → SQL·파일·설정·기존 보고서 파일 이관 → 무결성 해시 갱신 → 재기동 → 검증**의 12단계로 구성됐다. `--dry-run`과 PLAN/APPLY/SKIP 판정은 사이트 상태에 따른 재실행을 고려한 설계다. 설정 병합은 필요한 키만 변경하고, 보고서 다운로드 경로와 이미지/템플릿을 이관한다. 설치 가이드는 담당자가 사전 점검·적용·화면 확인·문제 시 되돌리기를 순서대로 할 수 있도록 작성됐다.

`PATCH.md` 기록상 검증 서버에서는 적용→재점검→rollback→재적용 리허설과 자동 검증을 수행했다. 2026-10-01 jar 갱신 검증은 한 환경에서 **22/22 OK**로 기록되고, 다른 환경의 초기 **20 OK/2 FAIL**은 날짜 변경에 따른 로그 롤오버를 검증기가 잘못 읽은 오탐으로 분석해 `patch.sh`의 로그 inode·크기 판별을 수정한 뒤 **22/22 OK**로 재실행했다. 이는 **패치의 검증 로직 자체를 수정한 사례**다. 문서에 운영 서버는 미적용으로 기재돼 있으므로 “고객 운영 전체 배포 완료”라고 쓰지 않는다.

`PACKAGE.md`는 기존 설치 패키지와 패치 결과의 차이, 순서, 해시/무결성, 재설치 결함·복구 경로를 정리한다. 다만 문서 안에는 백그라운드 에이전트가 수행한 단계와 사용자가 결정한 단계가 섞여 있고, 이 폴더만으로 외부 패키지에 실제 남아 있는 파일을 모두 재검증할 수 없다. 따라서 경력기술서에는 **신규 설치 패키지 분석·재구성 문서화 및 검증에 참여**한 범위로 표현하고, 개별 결함 수정의 직접 작성 여부는 별도 Git/파일 증빙을 붙일 때만 주장한다.

**근거 경로:** `03. kstv5/00. meta/00. kstv5 - development/docs/{README,HISTORY,PATCH,PACKAGE}.md`, `patch/{patch.sh,INSTALL_GUIDE.md}`, `reference/perf.py`, `db_diag.sh`, `sql_time.sh`. 원본에 포함된 서버 주소·계정·비밀번호·내부 배포 경로는 이직 자료로 옮기지 않는다.

##### 페이지 3 — 성능 문제를 다룬 방식

**헤드라인:** 반복 조회와 넓은 조회 범위를 줄이도록 경로를 바꿈

**사례 A, 장비 상태:** 장비별 N회 최근 로그 조회를 최근 1일 `create_time` 기준 장비별 MAX 집계와 배치 UPDATE로 변경. 전후 시간 측정치는 아직 없다.

**사례 B, 보고서:** KRO/KRS SQL·물리 L2 테이블 집계 경로를 조정하고 장비 IP 조인 등의 쿼리 구조를 수정. 트랜잭션 변경 후 잠금 문제를 보고 경계를 다시 조정했다.

**사례 C, 모니터링:** `(create_time, id)` 커서와 동일 시각 경계 보완으로 여러 L2 테이블을 순차 탐색. 최신 후보를 먼저 보고 충분한 결과를 확보하면 오래된 테이블을 건너뛴다.

**도식 아이디어:** `반복/전체 조회 → 기간 제한·배치/커서 조회`의 구조도. 막대 그래프를 넣는다면 실제 벤치마크 결과를 확보한 뒤에만 그린다.

##### 페이지 4 — 운영 안정성

**헤드라인:** 생성 중복과 재시작 잔여 상태를 처리

**시나리오 1:** 같은 보고서 종류·기간·장비(요약은 선택 섹션 포함)의 요청이 겹치면 중복 실행을 막고 실패 이력을 남긴다. 실행이 끝나면 `finally`로 잠금을 해제한다.

**시나리오 2:** 프로세스 재시작 시 미완료 보고서 이력을 실패로 정리하고 UUID 패턴의 임시 집계 테이블을 검사해 제거한다.

**제약 표기:** 이 잠금은 단일 JVM 안에서 작동한다. 다중 인스턴스 분산 잠금이라고 쓰지 않는다.

##### 페이지 5 — 대량 로그 내보내기

**헤드라인:** CSV/Excel 출력을 시간 구간·행 청크로 스트리밍

**흐름:** `데이터 실제 시각 범위 확인 → 600초 구간 분할 → 최대 5,000행 조회 → 동일 시각 경계/커서 처리 → 파일 writer 전달 → 행 수 기준 파일 분할`.

**차별점:** 정규화 로그와 원시 로그의 정렬 키가 달라 각각 동일 시각 보완과 `(create_time, seq)` 커서를 사용한다. 전체 결과를 한 리스트에 담지 않는 구조다.

**표현 제한:** 메모리 사용량/최대 성공 건수 수치는 아직 검증 자료가 없다.

##### 페이지 6 — 결과와 배운 점

**확인 가능한 결과:** 보고서 서비스 경계, 공통 생성·이력 UI, 중복 실행/재시작 정리, 관제 목록 커서 페이징, 청크·분할 출력 경로가 코드에 반영되었다.

**회고용 문장:** 데이터 양이 많은 레거시 제품에서는 한 SQL을 빠르게 만드는 것뿐 아니라 요청 단위, 잠금 범위, 시간 경계, 실패 후 정리까지 함께 설계해야 했다. 실제 개선율은 운영 측정 자료를 확보한 뒤 제시한다.

##### 페이지 7 — 취약점 점검 스크립트

**헤드라인:** 설정 점검을 항목별 BAT와 제품 DB 스크립트로 연결

**콘텐츠:** Windows/PC 항목 19개 BAT, 18개 Python. 에이전트가 실행하는 점검 로직과 DB의 스크립트 컬럼을 연결하고 `ok`/`fail` 결과 형식을 사용했다. IIS/FTP/DNS, 계정·서비스, SNMP, 로그·네트워크, SQL Server 정책 등 범위를 아이콘/카테고리로 표시한다. Python 18개에 포함된 BAT 본문이 동명 파일과 일치함을 확인했다. W-09는 BAT만 있고 `runall.sh`는 9개 Python만 실행한다.

**도식:** `항목 기준·가이드 → BAT 점검 로직 → 에이전트 실행 결과 → Python을 통한 DB 스크립트 반영 → 에이전트·서버 확인`. 마지막 시험 확인은 작업 절차이며 모든 항목의 통과 로그로 그리지 않는다.

##### 페이지 8 — 성능 측정에서 배운 점

**헤드라인:** 수치보다 먼저 측정 조건을 검증

**사례 1:** 고정된 검색 날짜가 실제 대량 데이터 구간을 비켜가던 문제를 최근 30일 기준으로 수정했다.

**사례 2:** 측정 도구의 `autocommit=False`가 대규모 단일 트랜잭션을 만들어 KRO07 병목을 과장했음을 찾아 수정했다.

**사례 3:** 쿼리 캐시가 만든 약 2ms 결과를 무효로 보고 `SQL_NO_CACHE`로 재측정했다. 파티션 수는 줄었지만 읽은 행 수·시간 개선이 작다는 최종 결론을 반영했다.

**실측 카드:** 특정 검증 환경에서 KRS API는 기존 3회 모두 600초 타임아웃에서 수정 후 3회 모두 완주(평균 6.6분). “600초→6.6분으로 빨라짐”보다는 **완주 가능 상태로 변경**으로 표현한다.

##### 페이지 9 — 패치·되돌리기

**헤드라인:** 폐쇄망 변경을 적용·검증·복구 가능한 절차로 구성

**흐름:** `dry-run/상태 확인 → 백업·rollback 생성 → 서비스 정지 → DB·파일·설정 반영 → 보고서 파일 이관/무결성 갱신 → 재시작 → 자동·수동 확인`.

**근거 카드:** 검증 서버의 적용→재점검→rollback→재적용 기록. jar 갱신 재검증 22/22 OK. 로그 롤오버 때문에 처음에는 검증기가 2건 오탐을 냈고 inode·크기 판별 수정 후 22/22 OK로 확인했다. 운영 전체 배포 완료로 표현하지 않는다.

#### 4. 면접 설명 순서와 답변 소재

1. **어떤 시스템이었나:** 보안 관제 V5의 로그·설비·취약점 정보를 보고서 및 화면으로 제공하는 제품이었다. 개인 Git 근거는 보고서·UI 서버 두 저장소에 집중된다.
2. **왜 보고서를 분리했나:** UI 서버 안의 생성 책임을 별도 보고서 서비스 호출로 옮겨 기능 경계를 분명히 했다. 별도 서비스의 네 종류 생성 API와 UI 요청 모델을 연결했다.
3. **성능 문제를 어떻게 찾았나:** 반복 장비 조회, 물리 로그 테이블 접근, 조인 조건, 임시 집계 테이블의 조회 범위를 patch와 SQL에서 확인했다. 전후 정량 측정치는 아직 확보하지 않았다.
4. **트랜잭션·락은 어떻게 다뤘나:** 트랜잭션 경계 변경 뒤 잠금 문제가 있어 일부 경계를 다시 조정했다. 같은 보고서 중복 요청은 단일 JVM 키 기반으로 차단하고 항상 잠금을 해제한다.
5. **커서 페이징에서 까다로운 점:** 여러 테이블의 동일 시각 로그가 LIMIT 경계에 걸리면 누락 가능성이 있어 해당 시각 전체를 다시 읽고 ID로 순서를 확정했다.
6. **대량 내보내기 설계 이유:** 전체 결과 적재 및 긴 단일 쿼리를 피하려 시간 구간과 행 수로 분할했다. 정규화/원시 로그의 정렬 키가 달라 처리도 나눴다.
7. **본인 역할의 경계:** `report-mgr`/`ui-svr`의 개인 커밋과 현재 코드로 확인되는 부분을 직접 개발 범위로 설명한다. 다른 13개 저장소 기능은 개인 구현으로 주장하지 않는다.
8. **취약점 항목은 무엇을 바꿨나:** IIS·DNS·SNMP·Windows 계정/로그/네트워크·SQL Server 설정의 항목별 BAT와 DB 반영용 Python을 수정했다. BAT 19개와 Python 18개가 있으며 W-09는 BAT만 있다. 실제 운영 반영률은 시험 로그로 별도 확인해야 한다.
9. **측정에서 잘못 판단한 경험은:** 고정 기간, 트랜잭션 자동 커밋, 쿼리 캐시가 각각 결과를 왜곡한 사례를 찾아 수정했다. 최종 파티션 프루닝 재측정에서 개선이 작다는 결과도 그대로 기록했다.
10. **패치 리스크는 어떻게 다뤘나:** 폐쇄망 환경에서 적용 전 상태와 자산을 검사하고, 백업·rollback을 만든 뒤 단계별로 적용했다. 검증기 오탐까지 수정했다. 운영 전면 적용을 완료했다고 주장하지 않는다.

#### 6. 표현 안전선

- “68건 커밋”은 추적 범위를 나타내는 내부 근거이며 성과 수치로 앞세우지 않는다.
- “속도 N배”, “메모리 N% 절감”, “장애 0건”, “정확도 N% 개선”은 실측 자료 전까지 사용하지 않는다.
- `report-mgr` 초기 커밋과 `ui-svr`의 대량 삭제/merge를 새 코드 개발량으로 환산하지 않는다.
- V5 고정 크론 스케줄러와 KSTV6 동적 스케줄러를 혼동하지 않는다.
- 고객·제품 내부 URL/DB 값·소스 캡처는 공개 포트폴리오에 그대로 넣지 않는다. 도식과 가명 화면으로 재구성한다.
- 검증 환경의 KRS 완주·패치 검증 수치는 환경/횟수/측정 오류 정정을 함께 적는다. 운영 서비스 전체의 성능 개선율로 환산하지 않는다.
- `PACKAGE.md`에 기록된 백그라운드 에이전트 수행분을 모두 개인 단독 코딩으로 표현하지 않는다. 직접 확인된 역할은 자료 정리·검증·패키징 작업 참여다.
